## 0. One correction to the prompt's premise

`SIH26047_CLAUDE_CODE_FINAL_BUILD_PROMPT.md` opens by describing the repository as *"an
existing 28-question intake prototype"* whose flow is `28 fixed questions → submit → summary`.

**That is not what is here.** No such prototype was ever committed. This repository was built
from the original SIH26047 brief and already contains an adaptive state machine, a provenance
choke point, a deterministic red-flag engine, OCR with a verification lane, FHIR emission, an
audit chain and a measured evaluation harness.

So the prompt's §4 ("audit the existing app") and §45 Phase 0 ("do not break the existing
28-question flow yet") describe a migration that does not apply. This document is the audit it
asks for, run against what the code actually is, so the gap table below is honest rather than
theatrical.

The prompt's *targets* remain the right yardstick, and the rest of this document measures
against them.

### The question flow is not fixed

51 questions across 9 sections live in `data/ontology/{core,ros,ayush}.yaml`. The state machine
in `app/modules/dialogue/machine.py` walks them and evaluates `ask_if` conditions against facts
already recorded, so the interview a patient actually sees depends on their answers. Typical
walks in the eval harness ask 29–49 questions of a possible 51+13.

**The LLM never decides what to ask next.** `test_machine_runs_with_the_llm_unavailable`
monkeypatches the model to raise and walks the entire interview.

### Where the summary is generated

`app/modules/summary/` — `assemble.py` builds it by deterministic template,
`prose.py` optionally smooths a section with the LLM, and `traceability.py` **fails generation
outright** if any clinical claim does not resolve to a `record_fact()` entry. `generate.py` is
the only entry point.

### What can be reused

All of it. The reuse question the prompt poses is about a prototype that does not exist here;
the relevant reuse table is [PORTED.md](PORTED.md), which records the ~1,100 lines carried over
from the SIH 25026 terminology service (audit chain, ABAC evaluator, mock IdP, `emit_coding()`
guard, FHIR outcomes, compose stack).

## C. What I deliberately did not build, and why

The prompt asks for 52 sections of work. Some of it would make this codebase worse, and the
brief's own §46 says to cut breadth before correctness. These are the calls I made:

**`TranslationBackend` protocol (§6).** It would have no consumer. Untranslated questions
already fall back to English *visibly* — the API sets `translationMissing` and the kiosk says
so (ADR-0007). Adding an abstraction with one mock implementation and no caller is exactly the
clutter that makes a codebase hard to read. When real translations arrive they go into the
YAML, and no Python changes.

**Caregiver / attendant mode (§27).** Genuinely useful in a real OPD, and it does not appear in
a 90-second demo. It is a `source_role` field on the span plus a UI toggle — a small,
well-understood addition to make when the demo is not the constraint.

**A separate "Simple Mode" toggle (§7).** The kiosk *is* simple mode. Adding a toggle implies
there is a worse default, and there isn't. The specific items still missing are a slow-speech
control and an "ask attendant for help" button, both cheap and both listed in §D.

**A web `/evaluation` page (§1.3).** The CLI harness plus `docs/EVALUATION.md` plus the jury
drawer already answer "show me the metrics" from three directions. A fourth would duplicate
numbers that must not drift apart.

## D. Gaps closed since this audit was started, and what remains

### D.1 Complaint-aware branching — closed, and the near-miss is worth recording

A cough is no longer asked about pain character or radiation. The first attempt at this was
**wrong in the dangerous direction** and the eval harness caught it within one run.

That version required the complaint to *be* one of the pain options — an allow-list. It
therefore stopped asking about character and radiation for any complaint that did not map to a
coded option, which included two of the gold set's cardiac emergencies: *"just a little
discomfort, my wife made me come"* and *"there is a tightness across my chest since dawn"*.
Those are exactly the patients for whom "does it travel to your jaw?" is the question that
matters.

The rule now excludes by **deny-list**: skip the pain questions only when the complaint is
known to be fever, cough, weakness, skin or a check-up. An unknown complaint gets *more*
questions, never fewer — the same recall bias that governs the red-flag rules. Expressing it
needed one nested `any` inside `all` in the condition DSL, which is the minimum boolean nesting
that lets branching be recall-biased at all.

### D.2 FHIR preview — closed

`GET /sessions/{ref}/fhir/preview` builds the bundle and returns it without transmitting or
committing anything. Invariant 4 is untouched, and two tests hold that line: the preview does
not reach the stub receiver, and a patient token cannot call it.

### Still outstanding

1. **Fact-level confirm / reject (§17).** Edit exists; an explicit per-fact accept is a
   different clinical gesture and belongs on the summary line.
2. **Consultation-type choice for AYUSH (§21).** Currently a consent scope, which buries it.
   It deserves to be a first-screen choice.
3. **Slow-speech and "ask attendant for help" (§7).** Two buttons; real accessibility value.
4. **`questions_skipped_due_to_existing_fact` (§30).** The behaviour exists; the metric that
   proves it does not.
5. **The label-word matching weakness** diagnosed in `EVALUATION.md` — deliberately unfixed
   until there is fresh held-out data to measure the fix against.
